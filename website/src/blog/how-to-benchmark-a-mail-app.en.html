Anyone can publish a chart where their product wins. We wanted numbers we could defend line by line, so before measuring anything we wrote down the rules, and then we broke several of them by accident. This is both lists.

The six rules

  1. The same mail. Every app gets one account and nothing else: a mailbox of 20,000 generated messages, identical byte for byte. A script fills it and prints a fingerprint of the set, which is published with the results.
  2. A clean user. A user account made for the test, each app freshly installed and left on its default settings.
  3. A quiet computer. Plugged in, nothing else open, one app at a time.
  4. Everything is stated. The date, the computer, the system, each app’s version and the exact version of the test.
  5. Every app, every number. Nothing is left out because Regards loses it.
  6. Run again at each release. Old results stay in the repository.

Measuring from the outside

The test does not use any app’s own instruments, ours included. It watches each app the way you would with a stopwatch: when a window appears, when what it shows stops changing, how much processor time and memory its processes use, how much disk it takes. An app is counted with every process it starts, so nobody looks lighter by hiding work in a helper.

The five mistakes

1. Our editor made two apps quit. The first run reported that Spark and Mailspring never opened a window. They had started and exited at once: the test was launched from a code editor that sets a variable which tells apps of their kind to behave as a command-line tool. The test now clears it.

2. We counted a stranger. One app showed 347 seconds of processor time for a launch. The test had mistaken an unrelated long-running program for one of the app’s helpers. Processes are now matched by the folder they are installed in.

3. Watching changed the result. To know when a window has finished drawing, the test takes small pictures of it. Taking a picture makes an app draw, which is work it would not do alone, and every app looked busy for three extra seconds. Launch time and processor time are now measured in separate launches, and nobody is watching during the second kind.

4. We measured the wrong Thunderbird. Two versions were installed, and the account had been added in the other one. Our first Thunderbird numbers were for an app with no mail. We measured again and corrected the results; the mistake is recorded in the result file.

5. Regards refused to start, sometimes. A few launches showed no window at all. Regards allows one copy at a time, another copy was open on the same screen, and the new one politely handed over to it and left.

None of these favoured Regards in the end, and one of them was hiding a result that did not flatter us. That is the argument for the rules: you find your own errors only if you are looking for them.

Two rules we have not fully kept yet

This first run was made while the computer was in use, not on a quiet one, and Thunderbird was measured in its beta version because that is where the account was. Neither changes who comes first, but both are against our own rules, so both are written in the result files. The run will be redone properly at the next release of Regards.

What the test does not say

  • How fast each app fetches a mailbox for the first time, opens a message or searches. Those need each app to be driven, and are next.
  • The first launch after the computer starts, which is slower for every app.
  • Anything about macOS or Linux yet.
  • Anything about your computer. For that, run it.

Run it yourself

# get the code
> git clone https://github.com/lucienPochon/regards
> cd regards

# measure the mail apps you have (Windows)
> powershell -ExecutionPolicy Bypass -File bench\compare-apps.ps1

The script closes and reopens your mail apps, so do not run it while a message is being sent. The method is described in the bench folder, with the raw results of every run. If you get different numbers, we want to see them.

The results themselves are in Regards opens in 0.89 seconds.
